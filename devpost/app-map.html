◉ Deadline Radar — App Map

What each file does and how a request flows through the app. Stdlib-only Python; the only networked step is refresh.

The two commands, end to end

refresh: urls.txt → cli.read_urls → fetch.fetch (network) → extract.extract (kernel) → store.save → data/watchlist.json report: data/watchlist.json → store.load → rank.rank(today) → render.render_table (stdout) → render.render_html → docs/index.html

Files

deadline_radar/extract.pyThe kernel. HTML→text via html.parser (script/style stripped), then proximity heuristics: dates near deadline keywords → deadline; largest currency amount near prize keywords → prize. Site-agnostic by design.
deadline_radar/fetch.pyurllib fetch with User-Agent + 10s timeout. The only network code.
deadline_radar/store.pyJSON load/save. Atomic writes; corrupt files renamed aside, never discarded.
deadline_radar/rank.pydays_remaining against an injectable today; ordering: overdue first, soonest next, unknown last.
deadline_radar/render.pyFixed-width CLI table; self-contained dark HTML page (no JS, no external resources).
deadline_radar/cli.pyargparse + orchestration. Per-URL failure tolerance: failed fetch keeps prior data, flags the row !.
tests/fixtures/Offline HTML pages (devpost-like, grant-like, no-deadline, malformed). Tests never fetch.

A practice worth reusing

Inject the seam you can't test. cli.main(argv, fetcher=..., today=...) takes the network and the clock as parameters, so the whole pipeline — including the CLI itself — runs offline in tests with a fake fetcher and a fixed date. The production default (fetch_mod.fetch, date.today()) is one line at the seam. Next time a plan names an untestable boundary (network, clock, randomness), put the parameter there at spec time, not after the first painful test.
